# 情景记忆用余弦检索，先暴力全表，不引向量扩展

待办第 3 条（情景记忆向量检索）开工前的范围与选型决策。嵌入能力其实早就在库里
（`NobodyWhoGateway` 的 `Encoder`、`memories.embedding` 列都建好了），缺的只是
「把问题向量化 → 找最相关的记忆 → 塞进 800 token 预算」这一段。本 ADR 定这一段怎么接。

## 状态

accepted（第 0 步已落地；2026-11-26 真机标定回填，阈值从占位值改为实测值）

## 决策

1. **范围只做记忆检索（A 方案）**。文档知识库（`documents` / `chunks` 表）暂不接回：
   产品的定位是本地记忆陪聊，不是文档问答。表留着不动，等真要做文档再捡。
2. **相似度用余弦，维度固定 1024**。依据是模型文件自己的元数据（见下「标定」），
   不是文档抄来的数字；维度写进代码常量，模型换错时第一时间报错而不是静默出垃圾结果。
3. **存储用 SQLite BLOB + 内存全量暴力检索**，不引 sqlite-vec 一类扩展。
   一条 1024 维向量 4 KB，一千条记忆 4 MB；全量点积在真机上是毫秒级。
   等到「条目 > 2000」或「单次检索 p95 > 100 ms」再升级，理由写在这里，别提前上 native。
4. **schema v5（当前 4）：`memories` 加 `embedding_model` / `embedded_at`**。
   向量必须记清是谁算的——换模型或换量化后旧向量就是噪音，`model_id` 不一致的条目
   一律当作没算过，后台重算，绝不让两代向量混在一个索引里。
5. **先硬阈值筛，再混合排序**：`cos ≥ 0.50` 才进候选，然后按
   `0.85 × cosine + 0.15 × (importance / 5)` 排序，top-k = 5，按 token 预算截断。
   硬阈值是先决条件——真机实测「无关」对最高 0.385（四对验证），只靠加权会把噪音和
   真命中混在一档（推算见「标定」）。阈值不手填：标定报告按中点法给建议值（实测 0.48），
   工程上向上取到 0.50 留余量；换模型重标一次即得。importance 权重压到 0.15 也是同一个原因：它最多只能在 0.15 的
   区间里调次序，不能把一条无关但重要的记忆顶到相关记忆前面。
6. **一切都可降级**：嵌入模型没装、加载失败、单条编码超时 → 静默回退纯重要度路径，
   聊天和出字不受影响。这条是硬约束：装个 App 不该因为嵌入模型坏掉变成砖。
7. **嵌入在后台异步补齐**，不进聊天主路径。记忆写入、导入备份、模型切换后各触发一次
   补齐任务，聊天提问时只读现成的向量。

## 标定

### 已实证（2026-11-25，读 GGUF 头，未加载模型）

用 `tools/gguf_metadata.py` 解析 `Qwen3-Embedding-0.6B-Q8_0.gguf` 的前 40 MB
（HTTP Range 抓头部，没有下完 600 MB）：

| 项 | 实测值 | 含义 |
|---|---|---|
| `qwen3.embedding_length` | 1024 | 维度就是 1024，代码常量按这个写 |
| `qwen3.pooling_type` | 3 | last-token 池化，不是 mean |
| `token_embd.weight` | dims=[1024, 151669] | 确认是嵌入模型，不是 0.6B 生成模型 |
| `output_norm.weight` | dims=[1024] | 与上面的维度自洽 |
| `tokenizer.ggml.add_eos_token` | True | 分词器默认追加 EOS（见风险 1） |
| `tokenizer.ggml.bos_token_id` / `eos_token_id` | 151643 | 同一 token，Qwen 系列惯例 |

### 真机实测（2026-11-26，OnePlus PKR110 / Android 16 / arm64，设置 → 01 / MODEL → 「标定」）

| 项 | 实测 | 结论 |
|---|---|---|
| 维度 | 1024 | 与 GGUF 头一致，模型没选错 |
| 首次调用（含加载 640 MB） | 787 ms | 编码器惰性加载几乎无成本，不必启动预热 |
| 单条 | 58 ms | 每轮提问多 58 ms，可接受，不做缓存 |
| 批量 8 条 | 345 ms（43 ms/条） | 批量只快 26%，够后台补齐用，不值得为它改主路径 |
| 原始范数 | 113.41 | 模型不归一化，检索侧必须自己归一化 |
| 同句一致性 | 1.000000 | 确定性，检索结果可复现 |
| 批量 / 单条偏差 | 0.000000 | `encodeBatch` 与 `encode` 等价 |

相似度分布（7 组探针，全部落在预期档位）：

| 档位 | 实测余弦 |
|---|---|
| 高（同义改写 / 同义加词） | 0.957 / 0.932 |
| 中（地点相关 / 同城不同事 / 同类不同事） | 0.715 / 0.621 / 0.584 |
| 低（完全无关） | **0.385** |
| 跨语言（中文 ↔ 英文） | 0.856 |

**三条推论，直接改写了原计划：**

1. **噪音地板是 0.385，原占位阈值 0.35 在噪音下面，等于没筛。** 阈值定 **0.50**：
   高于地板 0.115，低于最低的「中」档 0.084，把无关挡在门外又不误杀沾边的。
2. **线性加权会被地板吃掉。** 用原来的 0.7/0.3：无关但重要度 5 的条目得
   `0.7×0.385+0.30 = 0.569`，能压过相关但重要度 1 的条目 `0.7×0.621+0.06 = 0.495`——
   排序直接反转。所以先硬阈值、再 0.85/0.15。
3. **指令前缀不值得加。** 0.6814 → 0.6843（+0.003），top1 不变。省掉前缀的 token 与编码成本。

风险 1（EOS 缺失）实测排除：同义改写在 0.957，池化正常。

### 第二轮补强：地板不能只靠一对（2026-11-26）

首轮唯一的问题是证据薄：7 组探针里只有**一对**「完全无关」，0.385 这个地板是单点。
补到 10 组（无关 4 对、并换锚点，避免只在「我住在杭州」这一句上过拟合）：
无关·天气 / 无关·工作 / 无关·搬家 / 无关·周末。

同时把阈值算法从「人眼比大小」改成报告自己算：

```
噪音地板 = max(无关对余弦)
最低中档 = min(中档对余弦)
建议阈值 = 两者中点（两侧余量相等，取两位小数）
```

**第二轮实测（2026-11-26，补强后）**：13 条探针、单条 56 ms、批量 41 ms/条、加载 911 ms。

四对无关的余弦是 **0.3848 / 0.3224 / 0.3579 / 0.3383**——最高分与首轮那一对
（0.3848）逐位相同，换了三个锚点也没顶上去。地板 = **0.385** 确认是实数，不是单点巧合；
其余三对落在 0.32–0.36，说明「无关」的分布是紧的，阈值偏离 0.385 一点就会开始漏筛。

报告给的建议阈值 **0.48**；工程取 **0.50**（向上取到 0.05 的整数倍，多留 0.02 余量，
宁可少召回一点，也不让无关条目混进 800 token 的稀缺预算）。
规则归规则、留余量归留余量，两个数都记在这里，别以后搞混。

批量/单条偏差这次是 **0.000547**（首轮 0）：仍远低于判定线 1e-3，是批量累加顺序的
浮点差异，不影响排序（离 0.50 的判定线还差两个数量级）。
另外两条自检：无关对少于 2 对时报告会写明「地板是单点证据」；
地板 ≥ 最低中档时判「分布塌陷」，直接不给阈值——宁可没有，也不给一个害人的数。

### 风险

1. **last-token 池化对末位 token 敏感**。若 nobodywho 侧分词不追加 EOS，向量质量会掉。
   信号：标定里「改写同义」那对拉不开（明显低于高相似档位）就该怀疑这里。
2. **指令前缀**：实测 +0.003、top1 不变（0.6814 → 0.6843），**明确不加**。
   Qwen3-Embedding 官方建议 query 加 `Instruct: …\nQuery: `，但对本项目这种短句
   检索没有收益，还多一层 tokenizer 成本。
3. **中文短句相似度整体偏高**（实测证实）：无关对 0.385、沾边对 0.58+，
   压缩在 0.38–0.96 这 0.58 的区间里。照搬英文经验的 0.7/0.8 会误杀大半命中；
   阈值和权重必须按这张实测表定，换模型就得重标。
4. **换模型/换量化必须全量重算**，靠决策 4 的 `embedding_model` 兜住。
5. **内存**：1000 条 × 4 KB = 4 MB，可接受；上万条才需要重新算这笔账。

## 后果

- `ChatService` 的 system 组装从「按重要度截断」变成「重要度 + 检索命中」，仍受
  800 token 预算约束，超出的命中不硬塞。
- 多一个 schema 迁移（v4 → v5，`AppDb.schemaVersion` 现在是 4）和一个后台补齐队列；迁移要能处理「有记忆但无向量」的旧库。
- 备份导出仍不携带向量（当前实现即如此）：导入后按 `model_id` 重新补齐，避免跨设备
  带着不同模型的向量跑。
- 暂不引入任何 native 依赖，Android/iOS 打包不变。
- 每轮提问多一次编码：实测 58 ms 计入首字延迟。这是检索的固定成本，
  预算里按 100 ms 留余量，不做优化。

  - `setMemoryEmbedding` 不碰 `updated_at`：补算不是用户改动，不该抢排序。
  - 脏 BLOB（长度不是 4 的倍数）跳过而非抛错：检索宁可少一条也不能崩。
  - 全量 138 例测试通过（`app_db_test` 新增 7 例，含 v4→v5 迁移）。
- **第 2 步（嵌入服务）**：完成 2026-11-26。
  - `EmbeddingService`：`backfill`（后台补齐）/ `loadIndex`（检索投影）/ `embedQuery`（查询编码）。
  - **没有待补就不加载编码器**：省掉 787 ms 加载与 640 MB 常驻，纯聊天用户零成本。
  - 并发触发合并成一轮（切页、导入、提取同时打也只跑一次），靠单飞 Future。
  - 批量条数与输入对不上 → **整批作废**：错位向量比没有向量更坏。
  - 查到的待补集合没有进展就收手，防止「写不进又一直查得到」的死循环。
  - 所有异常（加载失败、OOM、原生错误）只 `debugPrint` 留痕、不上抛；聊天路径对它零依赖。
  - 触发点收敛到 `AppState.loadMemories()`：写入、导入、提取都会经过这里，不用每处都记得调。
  - 换嵌入模型时按 `modelId` 重建服务；一条记忆只有一个向量列，换模型是**原地覆盖**，
    对旧模型而言这些条目重新变成「待补」（不是并存两套）。
  - 全量 147 例测试通过（`embedding_service_test` 新增 9 例）。

  - 全量 157 例测试通过（`memory_retrieval_test` 新增 10 例，含「0.7/0.3 会反转」的回归断言）。

### 真机验证（2026-11-26，OnePlus / Android 16）

- 升级安装后首次启动：`向量补算完成：4 条（…Qwen3-Embedding-0.6B-Q8_0.gguf）`——补算闭环。
- 每轮提问日志：`检索：索引 4 条，命中 0 条，最高分 0.385`。
- 当时库里 4 条记忆（用户儿子上大学 / 用户名字叫 Danny / 半夜饿 / 需要上班）与「I caught a cold」
  的逐条余弦是 0.385 / 0.359 / 0.356 / 0.329 —— **全部低于 0.50，全部被挡住**，
  与标定得到的噪音地板一致。这条日志是「阈值没定错」的现场证据，也是排查误检的入口。
- 顺带记一笔：9B 本地模型一条回答实测 49.3 s。检索的 58 ms 在这个量级面前不是问题，
  真正的延迟瓶颈仍然在端上生成。
