# 记忆提取改分批：一天的经历不该因为聊得久而消失

真实反馈：用户昨天聊了一整天去哪儿玩，聊完新建对话，再问「还记得我昨天去博物馆吗」，
模型不但不记得，还假装记得细节。查下来是三个问题叠在一起。

## 状态

accepted

## 问题拆解

1. **只取尾部 6 轮**（真凶）。`MemoryService.extractFromTurns` 把 `turns` 截成
   `sublist(length - 6)`——会话超过 6 轮，前面聊过的事**永远**进不了记忆。
   用户白天聊博物馆、晚上聊别的，新建对话时博物馆早被挤出窗口。
2. **prompt 只要「事实」**。原文案是「提取值得长期记住的用户事实」，虽然
   `kind` 里有 `event`，但没有一句说明「做过的事、去过的地方也要记」，
   小模型自然只挑稳定属性（名字、住址、工作）。
3. **没有记忆时没人拦着编**。记忆列表为空时 system 里什么约束都没有，
   问「还记得吗」小模型会顺着上下文编一段，表现成「假装记得」。

## 决策

1. **分批跑完整个会话**：每批 6 轮，从最早往后顺序推进，不再截尾。
   单次最多 12 批（72 轮），超出的轮次打日志留到下次——9B 上一批要几十秒，
   不设上限会让「新建对话」变成后台跑几分钟。
2. **某批解析失败就停手**：坏 JSON 多半意味着模型这轮已经跑偏，继续烧 token 没意义。
   停手前已写入的条目保留（不做回滚：记忆是增量事实，不该因为后面失败而丢）。
3. **prompt 标日期、明确要 event**：开头写「今天日期：YYYY-MM-DD」，
   把四类各自解释一遍，并要求事件写清日期、**一次性的经历也要提取**。
   日期由可注入的 `now()` 提供，测试里固定住，避免断言随日期漂移。
4. **补两句显式禁令**：
   - 有记忆时：`（以上是你能确定的全部记忆；没列到的事就说不记得，不要编。）`
   - 一条记忆都没有时：`（你还没有关于用户的记忆；不知道就说不记得，不要编。）`
     这句只在预算够时加，绝不为了它挤掉人设。
   两句都计入 800 token 预算（`fitMemoriesWithinBudget` 预留），否则截断会少算一段。
5. **不做游标**：每次提取都从头跑，靠现有 bigram 去重（阈值 0.6）把重复内容收敛成 update。
   代价是重复提取浪费一些生成调用；换来的是不需要改 schema、也不会因为游标写坏而漏轮次。
   真到了「会话几百轮」的量级再上 `sessions.extracted_upto`。

## 后果

- 会话越长，后台提取调用越多：40 轮 ≈ 7 批，9B 上可能两三分钟。
  属于「聊完就不用等」的后台任务，但要注意别在低端机上同时触发别的重活。
- 事件记忆开始出现（`kind=event`），正好能被 1.4.0 的向量检索捞到——
  「博物馆」这种词和检索问句的余弦通常能过 0.50。
- **已经丢掉的记忆找不回来**：手动提取只针对当前会话，旧会话没有入口重跑。
  真需要的话下一步做「从历史会话补提取」，那是独立功能，不在本次改动里。

## 测试

- `memory_service_test`：20 轮跑 4 批且首批是 `问题0`、末批是 `问题19`；
  某批坏 JSON 后不再消费后续脚本；prompt 含日期、`event 事件`、`只发生过一次也要记`。
- `chat_service_test`：有记忆时带收尾禁令，无记忆时带空记忆禁令，且禁令进预算。
- 全量 168 例通过。
