# 人设分两个槽位：本地小暖、云端傲娇鱼

2026-11-18 用户提出：平时聊天用 flash 更便宜；本地默认用短人设「小暖」，云端则用更长的「傲娇鱼」。这推翻了 ADR-0011「只有一张短人设」的部分前提——但原因不是人设要变复杂，而是**预算变了**：本地 800 token 装不下 2.3k 字的人设，云端 6000 token 装得下。

## 状态

accepted

## 决策

1. **两个槽位，不是多张卡**：`local`（本地模型）与 `cloud`（云端 API）各存一张人设，id 固定、名字可改。内容各自保存、互不覆盖；切后端只是换用对应槽位（ADR-0014 初版用「预设芯片」实现，用户反馈点一下就回默认值，改成槽位）。
2. **两种形态共存**：短人设仍是六字段（名字 / 性格 / 说话方式 / 口癖 / 称呼 / 边界）；长人设用整段 markdown（`PersonaCard.text`），适合云端。
3. **点槽位 = 切换，不是恢复**：点某一行会把对话切到那个后端；「恢复这一张」才回默认。改名会跟着显示在槽位上。
4. **system 预算按后端**：本地 800、云端 6000（`AppState.cloudSystemBudget`），云端上下文 64k，留足记忆空间。
5. **编辑器支持长文模式**：`text` 非空的人设进编辑器时显示整段文本框，不再拆六字段；预设芯片「傲娇鱼 / 小暖 / 小助 / 阿博」可一键切换。
6. **`text` 必须落盘**：ADR-0011 曾把 `text` 当成兼容字段，`toJson` 里没写它；这次补上，否则长人设读回来是空的。
7. **云端默认模型 `deepseek-flash`**：日常聊天便宜、够用；要更强在设置里改成 `deepseek-v4-pro`。

## 后果

- 单卡原则不变，但「卡」现在有两套体量；设置页会标出「长人设（云端合适，本地会被截断）」。
- 本地若强行选傲娇鱼，`buildSystemPromptWithinBudget` 会保留人设、把记忆挤掉——这是既有取舍，不新增自动降级。
- 傲娇鱼正文来自 DSH 插件 `dsh-persona-dafeiyu` 的本地库（`~/.dsh/storages/dsh-persona-dafeiyu/personas.json`），随仓库一起分发。
